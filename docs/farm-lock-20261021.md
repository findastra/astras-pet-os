Developers call the farm lock a **lockfile**, and the Friendly Farmer is the **package manager** (`skills/dev-mindset`).
Adding a pet is *installing a package*. Taking one away is *uninstalling* it. A pet's `needs` are its
*dependencies*.

## What is true today

1. **There are two kinds of farm folder.**
   - An **installed farm** is a copy of the release with no git.
     - On Windows it is `%LOCALAPPDATA%\Programs\astras-pet-os`.
     - On Linux it is `~/.local/share/astras-pet-os/farm/`, next to the release.
   - A **hub copy** is a fork or private copy in git. Astra's own farm is one: it runs from her hub folder, and its
     pets.json is the registry itself.
2. **On an installed farm, "a pet on the farm" means its entry in the farm's pets.json.** A draft pet also has its line
   in the desktop draft list. With them come its desktop pet, its pet program page and its Markdown pet. Its own code is
   not downloaded: it stays on GitHub.
   - The installer keeps only the chosen entries (`Set-FarmPets`).
   - It writes the choice into `install-receipt.json` (on Linux, `farm-receipt.json`).
3. **On Windows, an install keeps no full list of pets.** After `Set-FarmPets`, the release's own pets.json is gone
   from the install folder. To add a pet later today, you run the installer again from the unzipped release. On Linux
   the release stays whole.
4. **The installer does not read `needs`.** Checked with the farm setup the installer shares:
   `-Farm Scratch -Pets evidence-locker` gives the Friendly Farmer and Forensic Ferret, without Log Lynx. Forensic
   Ferret's needs say Log Lynx is required.
5. **What a pet pack carries:**
   - Its layout is `<repo>/` next to `astras-pet-os/`, the places a farm keeps them.
   - Its manifest holds every file's SHA-256, the pet's commit, tag and version, and its needs, with their names.
   - It does **not** carry the pet's pets.json entry.
   - It is **not signed**, so its hashes prove the zip is whole, not who made it (PROVENANCE.md).
6. **What the needs say today:**
   - Required pets: Packet Piranha, Forensic Ferret and Kernel Koala need Log Lynx (`log-den`). Log Lynx and Packet
     Piranha name each other, but only one way is required.
   - The core: Startup Star is on every pet with a desktop pet (required only for Claude Bot). The Friendly Farmer's
     daily round is required for GitHub Goldfish.
   - Programs are named by their System Map node. The map does not say how to find a program on a computer, so the
     Farmer cannot check that one is installed.
7. **The hub and 41 of the 42 pets' repos are private** (pets.json, since 2026-10-20). Only Discord Damsel's repo,
   `findastra-discord-presence`, is public. So today:
   - a pack of any other pet needs `--private`;
   - someone who cannot see Astra's repos cannot check a pack against GitHub.
8. **The rules this must keep:**
   - From `skills/farm-security`: *"Nobody becomes an animal by saying so."*
   - A pet from someone else *"never runs on a farm until it is signed, checked, quarantined (read-only) and adopted by
     that farm's owner."*
   - Farms never connect to each other.

## The proposal

### Two words first: the catalog and the farm

- **The catalog** is the list of pets this farm may have: the pets.json of its release or of its own hub copy. It is
  the core, so it changes only through a pull request that the farm's L4 merges. Developers call it the *package
  registry*.
- **The farm** is the list of pets on this computer now: the farm's own pets.json that the desktop pets read, and the
  farm lock. Developers call it the *installed set*.
- **The Friendly Farmer's add and remove change only the farm.** A pet the catalog does not have cannot be added, from a
  pack either:
  - register it first, with a pull request in your own hub copy (MAKE-IT-YOURS.md, section 5);
  - a pet from another farm comes later, through the Kennel, once packs are signed.

### What the farm lock holds

One JSON file. Below is Dev's farm, set up from scratch, after she added Forensic Ferret from a pet pack. Log Lynx came
along because Forensic Ferret needs it.

```json
{
  "schema": "astras-pet-os-farm-lock-v1",
  "written_by": "the-farm-v1.0-farm-pets-v1.0",
  "updated": "2026-10-22T19:04:00-06:00",
  "farm": {
    "github_owner": "XxdevilishxX",
    "core": { "came_from": "installer", "version": "v0.3.0-beta", "commit": "7906b9c" },
    "mode": "farm",
    "os": "windows",
    "core_parts": { "startup-star": "on", "daily-round": "not on this farm" }
  },
  "pets": [
    { "repo": "astras-pet-os", "pet": "Friendly Farmer", "account": "XxdevilishxX", "core": true,
      "entry": { "came_from": "installer", "version": "v0.3.0-beta", "sha256": "…" },
      "code": null, "chosen": true, "needed_by": [] },
    { "repo": "evidence-locker", "pet": "Forensic Ferret", "account": "findastra",
      "entry": { "came_from": "installer", "version": "v0.3.0-beta", "sha256": "…" },
      "code": { "came_from": "pet-pack", "pack": "evidence-locker-pet-pack-20261022.zip", "pack_sha256": "…",
                "manifest_sha256": "…", "folder": "../evidence-locker", "version": "0.1.2-20261019",
                "commit": "…", "tag": null, "checked_against_github": true },
      "chosen": true, "needed_by": [],
      "needs": { "os": ["windows"], "pets": [{ "repo": "log-den", "how": "required" }], "core": [], "programs": [] },
      "missing": [] },
    { "repo": "log-den", "pet": "Log Lynx", "account": "findastra",
      "entry": { "came_from": "installer", "version": "v0.3.0-beta", "sha256": "…" },
      "code": null, "chosen": false, "needed_by": ["evidence-locker"], "missing": [] }
  ],
  "history": [
    { "at": "2026-10-22T19:04:00-06:00", "did": "add", "pets": ["evidence-locker", "log-den"],
      "from": "evidence-locker-pet-pack-20261022.zip" }
  ]
}
```

| Field | What it says | Why |
|---|---|---|
| `farm.core` | Which Astra's PetOS release the farm runs, and its commit | Every pet's entry came from it |
| `farm.mode`, `farm.os`, `farm.core_parts` | Farm or developer mode, this computer, and which core parts it has | The needs check reads them |
| `entry` | Where the pet's pets.json entry came from, and a SHA-256 of it as written | A hand edit shows up in `check` |
| `code` | Its own code, when it came from a pack: the pack's SHA-256, its manifest's SHA-256, the folder, version, commit and tag | Exactly which code runs. The manifest's hash covers every file (PROVENANCE.md: "a hash for each pet") |
| `chosen` | The owner picked it | `false` means it came only because another pet needs it |
| `needed_by` | The pets on this farm that need it | What keeps a removal from breaking them |
| `needs` | The needs as they were when it came in | A removal is checked offline |
| `missing` | Needs the Farmer could not add (question 4) | Said plainly, never hidden |
| `history` | Every add and remove, with the date and where it came from | The passport stamps (PROVENANCE.md) |

Paths are relative to the farm folder, so the file holds no personal folder path. Times are America/Denver.

**Where it lives (question 1, recommended):** in the farm's own folder on the computer, next to the install receipt.
It is never committed and never on GitHub. In a hub copy, `.gitignore` lists it.
- Why: a farm is one computer's install, and farms never connect. The lock describes what this computer runs.
- Developers know two things like it. A *lockfile* holds exact versions and hashes, so a farm can be proved unchanged
  and set up again. An *installed-packages database* (dpkg's status file on Linux) is also kept on the computer.
- The other way is to commit it in the farm's own hub copy, as developers commit `package-lock.json`.

**Its name (question 2):** `farm.lock` breaks Astra's file-name rule (lowercase, hyphens, the date before the
extension). Recommended: `farm-lock-20261021.json`, dated like `pet-pack-20261020.json`. The docs would then say
"the farm lock".

### How a pet comes in

A new tool of The Farm. Its working name is **farm-pets** (`the-farm-v1.0-farm-pets-v1.0`). Node.js runs it, like
make-it-yours and pet-packs. `plan` always comes first and changes nothing. `--yes` does exactly what the plan showed,
as with the pet-privatizer.

```
node scripts/farm-pets-<date>.mjs plan add log-den
node scripts/farm-pets-<date>.mjs add log-den --yes
node scripts/farm-pets-<date>.mjs plan add evidence-locker-pet-pack-20261022.zip
node scripts/farm-pets-<date>.mjs plan remove log-den
node scripts/farm-pets-<date>.mjs remove log-den --yes
node scripts/farm-pets-<date>.mjs check
node scripts/farm-pets-<date>.mjs lock
```

**From the installer's own pets (the catalog)**

- The Farmer writes the pet's entry into the farm's pets.json from the catalog, exactly as the installer would. A
  draft pet also gets its line in the draft list.
- He records it in the farm lock and restarts Startup Star so its desktop pet appears. The installer does the same
  when it is run again.
- No code is downloaded, as with the installer: the pet's page, pictures, desktop pet and Markdown pet are already in
  the release.
- On Windows this needs the catalog, so the installer keeps the release's own pets.json and draft list, unfiltered,
  in the install folder. On Linux the release already keeps them.

**From a pet pack**

1. **The Farmer checks the pack:**
   - every file's CRC and SHA-256 against its manifest;
   - its pet is in the catalog;
   - its code comes from the account the catalog says owns that pet (`ownerOf()`), so a lookalike repo on another
     account is refused;
   - the pack scan runs again (keys, tokens, personal folder paths, local service addresses);
   - its code is checked against the pet's own repo on GitHub (question 3).
2. **The pet's code goes into a folder named after its repo, next to the farm folder.** That is where its own programs
   look for `..\astras-pet-os\`; on Windows, `%LOCALAPPDATA%\Programs\evidence-locker`.
   - He never writes over a folder the farm lock does not list, such as someone's own clone.
   - The pack's pictures, page and Markdown pet are used only when the farm has none for that pet. A pack never
     replaces a picture the farm already has: the hub stays the one art source.
3. **The entry comes from the catalog, not from the pack.** It is written only when the pet is not on the farm yet.
4. **Nothing from a pack runs by itself.** The Farmer never starts a pet's own program and never adds it to start with
   Windows. That is the quarantine: the owner runs it from its README when they choose.
5. **A pack of a pet that is already on the farm, at another version, is an update.** The plan shows the version and
   commit it changes from and to.

### How its needs are checked, in this order

1. **The pet itself.** It is in the catalog and is an animal (the animal guard). It is not a core pet (they are
   always on the farm). It is not Claude Bot, whose art is private and never in a release.
2. **Required pets, all the way down.** For each required pet, then each pet that one requires, and so on:
   - on the farm already: fine;
   - in the catalog: it comes in too, with `needed_by`, from the same place (the installer's pets, or a pack that the
     owner names);
   - nowhere: he stops and names it, and where to get it. He never fetches anything by himself.

   Optional pets never pull anything in. The plan says which are already here and which are not. A loop of required
   pets stops the plan (there is none today). Pets go first because each pet that comes along brings needs of its own;
   the next two steps check the whole set at once.
3. **This computer and the core**, for every pet in the set:
   - `os`: a pet whose own program does not run on this computer stops. Its pack still opens its page anywhere.
   - Startup Star: a developer-mode farm has no desktop pets. An optional Startup Star is noted ("no desktop pet in
     developer mode"), and a required one stops.
   - The daily round runs only in a hub copy on GitHub, so an installed farm says "not on this farm" (question 4).
4. **Programs.** The Farmer never installs a third-party program: a pet's ring may read and run them, never write them.
   He lists each one, required first, with its `why` (question 4).

Then the plan is **one list**: every pet that comes in and why, what is already here, and what is missing. One `--yes`
covers it. On Dev's farm:

```
Forensic Ferret (evidence-locker) from evidence-locker-pet-pack-20261022.zip: 0.1.2-20261019, commit abc1234,
  the same files as findastra/evidence-locker at that commit.
  Needs Log Lynx (log-den, required): not on your farm; it comes from your installer's pets too.
  Works better with Packet Piranha (packet-river, optional): not on your farm. Add it later if you like.
  Runs on Windows 10 or 11: this computer is Windows.
  Desktop pets: Startup Star restarts so Forensic Ferret and Log Lynx appear.
Add with --yes.
```

### How a pet leaves without breaking another

1. **The pets that need it.** The Farmer reads `needed_by` and the needs in the farm lock, so this works offline.
   - If a pet on the farm **requires** it, he stops and names them: *"Forensic Ferret and Packet Piranha need Log Lynx.
     Take them away first, or all three together with --with-dependents"* (question 5).
   - A pet that only lists it as **optional** stays. The plan says what it loses.
2. **The pets that came only for it.** A pet with `chosen: false` that nothing else needs any more is listed, never
   taken away silently. One more yes takes it too (`--and-unneeded`). Developers know this as apt's *autoremove*.
3. **What goes:**
   - the entry in the farm's pets.json and its line in the draft list;
   - the code folder, only when the farm lock lists it and every file still matches the pack's manifest. A changed
     folder is kept and named, as the uninstaller keeps anything that is not its own;
   - the desktop pet, when Startup Star restarts.
4. **What never goes:**
   - a core pet;
   - the pet's data on this computer (the plan says where it is), as the uninstaller keeps settings;
   - its pictures in the hub;
   - anything on GitHub: the pet's repo stays as it is.

### `check` and `lock`

- **`check`** changes nothing. It compares the farm lock with what is on the computer:
  - every pack file against its manifest, and every manifest against the lock;
  - every entry against its hash;
  - every `needed_by`.

  It names any drift, such as a hand edit or a missing file. Developers know this as verifying an install.
- **`lock`** writes the farm lock for a farm that has none, such as an install made before the farm lock existed. On a
  hub copy it writes one without changing anything: every registered pet, with the commit of its clone next to the hub
  when there is one, and a note when the clone has changes not committed.

### The installer and the Linux package

- **Setting up a farm writes its first farm lock.** It records the core pets and the chosen ones, from the release, at
  its version and commit. One writer in Node (`farm-setup`) and its twin in the installer's PowerShell, tested to write
  the same lock, as `test/linux-package-test-20261019.mjs` already checks that both list the same pets.
- **Picking a pet ticks the pets it needs (question 6).** Picking Forensic Ferret ticks Log Lynx, locked, with "needed
  by Forensic Ferret". `-Pets evidence-locker` brings Log Lynx along and says so.
- **Running the installer again starts from the farm lock.** The window opens with the farm's pets ticked. Code from
  packs is kept, because it sits outside the install folder.
- **Uninstalling** also removes the pack folders the farm lock lists, when they are unchanged, then the install folder.
  Data is kept unless `-RemoveSettings`, as today.

## Risks, plainly

- **Two writers of one file.** The installer (PowerShell) and the Farmer (Node) both write the farm lock. One format and
  a test that both write the same lock keep them in step.
- **An unsigned pack.** Hashes prove the zip is whole. The check against GitHub proves the code is the pet's own at that
  commit, but only where this farm can read the pet's repo. Signing is what will prove who made a pack.
- **Hand edits.** If someone edits the farm's pets.json by hand, `check` names it. The farm lock never "fixes" it
  silently.
- **These are checks in the farm's own tools**, not a lock against a person. GitHub's permissions are what protect each
  account's repos.
